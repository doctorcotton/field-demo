## 授权配置

凭证不是字段捷径的必选项，取决于字段捷径代码是否依赖其他三方平台的凭证以及是否需要托管到平台侧。

- 对于平台[已接入](https://feishu.feishu.cn/docx/SZFpd9v6EoHMI7xEhWhckLLfnBh#share-WTFzd4z2EoHGalxzI9Ac8e4qnSg)的凭证类型，开发者按照本文指引定义具体的插件接口。
- 对于平台未接入的凭证类型，开发者如有需要，可提需求给平台，平台经过评估后决定是否接入。新接入凭证，开发者需要提供如下信息：
  - 凭证类型（ApiKey，Oauth）
  - 凭证使用相关文档
  - 如果凭证账号展示三方平台的账号信息，还需额外提供用于拉取三方账号信息的 API。并指定需要展示的字段

### APIKey 授权模式

#### 支持的授权模式

目前多维表格支持以下几种 APIKey 授权模式：

##### 1. HeaderBearerToken

用户输入 APIKey 后，多维表格框架在请求时会在 header 中带上请求头：`Authorization: Bearer APIKey`

**代码示例**：

```typescript
import { basekit, AuthorizationType } from '@lark-opdev/block-basekit-server-api';

basekit.addField({
  authorizations: [
    {
      id: 'auth_id_1',  // 授权的 id，用于 context.fetch 第三个参数以区分该请求使用哪个授权
      platform: 'baidu',  // 需要与之授权的平台，比如 baidu（必须要是已经支持的三方凭证）
      type: AuthorizationType.HeaderBearerToken,
      required: false,  // 设置为选填，用户如果填了授权信息，请求中则会携带授权信息，否则不带授权信息
      instructionsUrl: "https://www.feishu.com",  // 帮助链接，告诉使用者如何填写这个 apikey
      label: '测试授权',
      icon: {
        light: '',
        dark: ''
      }
    }
  ],
  execute: async (params, context) => {
    const url = 'https://example.com/api';
    // 通过指定 context.fetch 第 3 个参数为授权 id：auth_id_1
    // 则会在请求头带上 Authorization: Bearer APIKey
    const res = await context.fetch(url, {
      method: 'POST',
    }, 'auth_id_1');  // 第三个参数为某个授权的 id
  },
});
```

**本地调试配置（config.json）**：

```json
{
  "authorizations": [
    {
      "id": "auth_id_1",
      "apiKey": "AAAAAA"
    }
  ]
}
```

##### 2. Basic

用户输入用户名和密码，多维表格框架在请求时在 header 中带上请求头：`Authorization: Basic <base64 encoded username:password>`

**代码示例**：

```typescript
basekit.addField({
  authorizations: [
    {
      id: 'auth_id_1',
      platform: 'baidu',
      type: AuthorizationType.Basic,
      required: false,
      params: {
        usernamePlaceholder: '请输入用户名',
        passwordPlaceholder: '请输入密码',
      },
      instructionsUrl: "https://www.feishu.com",
      label: '测试授权',
      icon: {
        light: '',
        dark: ''
      }
    }
  ],
  execute: async (params, context) => {
    const url = 'https://example.com/api';
    // 通过指定 context.fetch 第 3 个参数为授权 id：auth_id_1
    // 则会在请求头带上 Authorization: Basic <base64 encoded username:password>
    const res = await context.fetch(url, {
      method: 'POST',
    }, 'auth_id_1');
  },
});
```

**本地调试配置（config.json）**：

```json
{
  "authorizations": [
    {
      "id": "auth_id_1",
      "username": "testuser",
      "password": "testpass"
    }
  ]
}
```

##### 3. MultiHeaderToken

用户可以输入多个 key，多维表格框架会在你请求时带上请求头。

**代码示例**：

```typescript

    {
      id: 'auth_id_1',

    const res = await context.fetch(url, {
      method: 'POST',
    }, 'auth_id_1');

});
```

##### 5. Custom

用户可以输入多个 key，由你指定组装到 url 或 body 中（不包含 headers）。

**代码示例**：

```typescript
basekit.addField({
  authorizations: [
    {
      id: 'auth_id_1',
      platform: 'baidu',
      type: AuthorizationType.Custom,
      required: false,
      params: [
        { key: "id", placeholder: "id" },
        { key: "token", placeholder: "token" },
      ],
      instructionsUrl: "https://www.feishu.com",
      label: '测试授权',
      icon: {
        light: '',
        dark: ''
      }
    }
  ],
  execute: async (params, context) => {
    const url = 'https://api.example.com/api';
    // 通过指定 context.fetch 第 3 个参数为授权 id：auth_id_1
    // 则会自动替换 url、body 中的 {{id}}、{{token}}
    // 注意：{{}} 不可被编码，否则将不会进行替换
    const res = await context.fetch(url + '?id={{id}}&token={{token}}', {
      method: 'POST',
      body: '这是id:{{id}}。这是token:{{token}}'
    }, 'auth_id_1');
  },
});
```

**本地调试配置（config.json）**（按照 params 中的顺序一一对应）：

```json
{
  "authorizations": [
    {
      "id": "auth_id_1",
      "id": "AAAAAA",
      "token": "BBBBBBB"
    }
  ]
}
```

### 开发阶段本地调试授权

在开发阶段暂不支持直接显示授权 UI 界面并调试。仅支持通过设置 `config.json` 来进行模拟调试：`config.json` 中的配置将模拟用户的授权输入。

**重要**：`config.json` 由系统读取，代码不直接读取。

如果要调试非必填的授权项，用户未填写授权的情况，则可以在 `config.json` 中将对应的授权信息设置为空字符串即可。

根据不同的授权类型，在项目根目录中修改 `config.json` 中的 `authorizations` 为对应的结构即可在捷径调试阶段注入 `config.json` 中的模拟授权信息。

每种授权类型的授权 mock 参数格式详见上方各授权模式的"本地调试配置"部分。

## 捷径流量标识

目前开发者在插件里通常会通过 http 协议调用自己服务端的 API，某些情况下，为了适配捷径插件，API 无任何校验，为了防止被其他恶意流量，base 侧目前支持三方开发者识别流量来源于 base。

具体的实现方式是：平台侧通过私钥签名一份数据，开发者通过平台暴露的公钥对数据进行验签来确保流量来源于 base。

### 具体做法

1. 在捷径请求中同时将 `context.baseSignature` 和 `context.packID` 带上。
2. 服务端对 `baseSignature` 验签后再比较其中的 `packID`，如果验签通过且 `packID` 一致，则表示该请求是来自 `packID` 的捷径插件。

**注意**：在本地调试开发阶段，`baseSignature` 是一个固定的值，每个开发者拿到的值都是一样的。

### 流量标识数据格式

流量标识数据如下：

```
eyJzb3VyY2UiOiJiYXNlIiwidmVyc2lvbiI6InYxIiwicGFja0lEIjoicmVwbGl0XzNlNWQwYjU5MGZlZTIzZjMiLCJleHAiOjE3MjQ1OTE3Njk2NDB9.eyJzb3VyY2UiOiJiYXNlIiwidmVyc2lvbiI6InYxIiwicGFja0lEIjoicmVwbGl0XzNlNWQwYjU5MGZlZTIzZjMiLCJleHAiOjE3MjQ1OTE3Njk2NDB9
```

**数据生成说明**：

平台侧基于如下 JSON 数据：

```json
{
    "source": "base",   // 来源标识，表示流量来源于 base
    "version": "v1",    // 数据版本，目前站定 v1
    "packID": "",       // 插件实体 id 表示，标识流量来源于某个插件
    "exp": 343434       // 过期时间，生成规则是 now+10min
}
```

**签名步骤**：

1. 对上述数据序列化，得到 `srcData`
2. 对上述数据 `srcData`，先使用 sha256 进行 hash，然后用 rsa 私钥，对 hash 后的数据进行签名，签名后的数据为 `srcSignData`
3. 对第一步的数据 `srcData` 进行 base64.URLEncoding 编码，得到 `srcBase64Data`
4. 对第二步的数据 `srcSignData` 进行 base64.URLEncoding 编码，得到 `srcBase64SignData`
5. 对第三步和第四步得到的数据通过 `.` 进行连接：`srcBase64Data.srcBase64SignData`

## 同步&异步执行插件

不同类型的插件，实际执行的时间会存在很大差异。比如一般 AI 生成类的插件，执行时间会比较久，经常出现超过一分钟的情况。目前插件平台侧在等待插件在沙箱执行结果时，有两种方式可选：同步、异步等待。因此插件发布时，可以选择插件的执行方式。

### 两种方式的差异

| 方式 | 说明 |
| --- | --- |
| **同步** | - 等待沙箱执行，超时时间为 58s，超时会导致本次内容生成失败<br>- 限流时，限制的是 QPS（参考限流章节） |
| **异步** | - 等待沙箱执行，超时时间为 15min，超时会导致本次内容生成失败<br>- 限流时，限制的是并发数（参考限流章节） |

## 限流配置

对于插件，考虑到插件侧能够承受的流量存在一定的限制，因此提供了限流的能力，目前主要提供两个维度（插件、租户），共三个限流值的配置。

### 配置结构

```json
{
    "concurrencyLimit": 100,        // 插件级别限流
    "concurrencyTenantLimit": 10,  // 插件、租户级别限流
    "concurrencyTenantLimitMap": {
        "1": 1000  // 指定租户配置限流
    }
}
```

**说明**：插件执行时，`concurrencyLimit` 与 `concurrencyTenantLimit` 两者需要同时满足，即两者任意一个校验失败即视为失败。`concurrencyTenantLimitMap` 独立于前两个配置之外，命中该配置的租户，不受前两个配置值的限制。

### 限制值的含义

限制值的含义受插件执行方式（异步、同步）影响：

| 执行方式 | 限制含义 |
| --- | --- |
| **同步** | 限制调度到下游的并发值，同一时间最多只有指定数量的流量到插件侧 |
| **异步** | 限制调度到下游的 QPS，每 s 内，最多只有指定数量的流量到插件 |

**说明**：之所以同步、异步限制存在差异，主要是考虑异步通常执行时间较长，下游通常只能接受固定数量的执行任务。同步因为执行时间较短，因此采用了 QPS 限制。

## 国际化（i18n）

支持通过 `basekit.addField` 声明国际化资源，通过 `t` 方法使用国际化 key，目前支持中文（`zh-CN`）、英文（`en-US`）、日文（`ja-JP`），如果当前的语言环境不属于其中 3 种，则会使用默认英文的语言资源。

### 配置示例

```typescript
import { basekit, FieldType, field } from '@lark-opdev/block-basekit-server-api';
const { t } = field;

basekit.addField({
    i18n: {
        messages: {
            // 指定中文资源
            'zh-CN': {
                "scene": "场景",
                "name": "附件名称"
            },
            // 指定英文资源
            'en-US': {
                "scene": "Scene",
                "name": "Attachment Name"
            },
            'ja-JP': {
                "scene": "シーン",
                "name": "お名前"
            }
        },
    },
    formItems: [
        {
            label: t('scene'),  // 使用 t(i18n_key) 指定国际化资源
            // ...
        },
    ],
    resultType: {
        type: FieldType.Object,
        extra: {
            properties: [
                {
                    key: 'name',
                    type: FieldType.Text,
                    title: t('name'),  // 使用 t(i18n_key) 指定国际化资源
```

## ⚠️ 重要注意事项

### 格式修改后必须重新创建字段

#### 问题描述

如果字段的输入输出格式有修改，多维表格会缓存旧配置，导致数据格式不匹配、字段读取失败等 bug。

#### 需要重新创建的情况

以下任何情况都需要重新创建字段：

1. **formItems 中字段的 key 改变**
   - 例如：`key: 'baseUrl'` 改为 `key: 'url'`

2. **formItems 中字段的 component 类型改变**
   - 例如：`FieldComponent.Input` 改为 `FieldComponent.FieldSelect`

3. **resultType 的类型改变**
   - 例如：`FieldType.Text` 改为 `FieldType.Object`

4. **resultType.properties 结构改变**（Object 类型）
   - 例如：添加、删除或修改 properties 中的属性

5. **formItems 中字段数量增减**
   - 例如：从 2 个字段增加到 3 个字段

#### 操作步骤

1. **删除多维表格中已创建的字段捷径**
2. **重新创建字段捷径**

#### 原因说明

多维表格会缓存字段配置结构，代码修改不会自动更新已创建的字段。已创建的字段会继续使用旧的配置结构，导致：

- 数据格式不匹配
- 字段读取失败（undefined）
- 返回数据无法正确写入

#### 常见错误

不重新创建字段会导致：

- `formItemParams` 中字段为 `undefined`
- 返回的数据无法写入多维表格
- 字段类型不匹配错误

### 字段名读取问题排查

#### 问题现象

`formItemParams` 中字段为 `undefined`，无法读取到字段值。

#### 检查清单

1. **config.json 中 mockData 的 key 是否与 formItems 中的 key 完全一致**（区分大小写）
   ```json
   // formItems 中定义
   { key: 'baseUrl', ... }
   
   // config.json 中必须匹配
   {
     "mockData": {
       "baseUrl": "https://example.com"  // ✅ 正确
       // "baseurl": "https://example.com"  // ❌ 错误（大小写不匹配）
     }
   }
   ```

2. **字段值的类型是否匹配**
   - Input 组件返回 `string`
   - FieldSelect 根据字段类型返回对应类型
   - SingleSelect 返回 `{label, value}`
   - MultipleSelect 返回 `[{label, value}]`

3. **formItems 中是否使用了 `t('key')` 而不是硬编码**
   - 确保使用 `label: t('key')` 而不是 `label: '硬编码文本'`

#### 解决方案

1. 确保 `mockData` 的 key 与 `formItems` 的 key 完全一致（区分大小写）
2. 检查组件返回的数据格式，确保类型匹配
3. 使用 `t('key')` 引用多语言文本

### 数据格式匹配问题

#### 各组件返回的数据类型

| 组件 | 返回类型 | 示例 |
| --- | --- | --- |
| Input | `string` | `"文本内容"` |
| FieldSelect (Number) | `number` | `123.45` |
| FieldSelect (Text) | `(ITextValue \| IUrlValue \| IMentionValue)[]` | 复杂对象数组 |
| FieldSelect (Attachment) | `AttachmentFieldValue[]` | `[{name, size, type, tmp_url}]` |
| SingleSelect | `{label, value}` | `{label: '苹果', value: 'apple'}` |
| MultipleSelect | `{label, value}[]` | `[{label: '苹果', value: 'apple'}]` |
| Radio | `{label, value}` | 与 SingleSelect 相同 |

#### 类型检查方法

```typescript
execute: async (formItemParams, context) => {
  const { baseUrl, account } = formItemParams;
  
  // 类型检查
  if (typeof baseUrl !== 'string') {
    console.log('baseUrl 类型错误，期望 string，实际:', typeof baseUrl);
  }
  
  if (typeof account !== 'number') {
    console.log('account 类型错误，期望 number，实际:', typeof account);
  }
  
  // ...
}
```

### 日志记录

#### 方式1：使用 debugLog（简单直接）

```typescript
function debugLog(arg: any, showContext = false) {
  if (!showContext) {
    console.log(JSON.stringify({ arg, logID: context.logID }), '\n');
    return;
  }
  console.log(JSON.stringify({
    formItemParams,
    context,
    arg
  }), '\n');
}

// 入口第一行日志，展示 formItemParams 和 context，方便调试
// 每次修改版本时，都需要修改日志版本号，方便定位问题
debugLog('=====start=====v1', true);
```

#### 方式2：使用 logger（推荐，更规范）

```typescript
import { getLogger } from './utils/logger';

const logger = getLogger('EXECUTE', context);

logger.info('开始执行', { 
  logID: context.logID,
  baseID: context.baseID,
  tableID: context.tableID
});

logger.debug('解析参数完成', {
  hasBaseUrl: !!baseUrl,
  baseUrlType: typeof baseUrl
});

logger.error('执行失败', { error });
```

#### 最佳实践

1. **入口记录完整上下文**：在 execute 函数第一行记录 `formItemParams` 和 `context`
2. **使用结构化日志**：使用 `JSON.stringify` 格式化日志
3. **版本号管理**：每次修改代码时更新日志版本号（如 `=====start=====v2`）
4. **日志级别控制**：使用 `FAAS_LOG_LEVEL` 环境变量控制日志级别

### 错误处理

#### 使用明确的错误码

```typescript
// ✅ 正确：使用明确的错误码
if (!baseUrl || typeof baseUrl !== 'string') {
  return {
    code: FieldCode.ConfigError,  // 配置错误
    data: null
  };
}

// ❌ 错误：不要使用通用的 Error
if (!baseUrl) {
  return {
    code: FieldCode.Error,  // 太泛化
    data: null
  };
}
```

#### 不要通过 msg 向用户传递错误

```typescript
// ❌ 错误：msg 不会向用户显示
return {
  code: FieldCode.Error,
  msg: '用户友好的错误信息'  // 用户看不到
};

// ✅ 正确：使用 code 传递错误，或把错误信息放在 data 中
return {
  code: FieldCode.ConfigError,  // 使用明确的错误码
  data: null
};

// ✅ 或者：业务错误放在 data 中返回（使用 Success code）
return {
  code: FieldCode.Success,
  data: {
    id: `错误原因：${errorMessage}`,
    // ...
  }
};
```

#### 错误码选择指南

| 错误情况 | 错误码 | 说明 |
| --- | --- | --- |
| 用户配置不合法 | `FieldCode.ConfigError` | 用户在配置面板选择的值不合法 |
| 授权失败 | `FieldCode.AuthorizationError` | 授权错误 |
| 付费错误 | `FieldCode.PayError` | 付费错误异常 |
| 限流 | `FieldCode.RateLimit` | 限流 |
| quota 耗尽 | `FieldCode.QuotaExhausted` | quota 耗尽 |
| 参数错误 | `FieldCode.InvalidArgument` | 用户所选配置的内容合法，但是代码中未兼容等情况 |
| 其他错误 | `FieldCode.Error` | 如果前面的 code 值都不符合，才考虑使用通用的报错 code |

### fetch 请求

#### 最佳实践

1. **先 text() 再 JSON.parse()**：避免非 JSON 响应导致解析失败
   ```typescript
   const res = await context.fetch(url);
   const resText = await res.text();  // 先转换为文本
   return JSON.parse(resText);  // 再解析 JSON
   ```

2. **记录请求和响应日志**：便于调试和排查问题
   ```typescript
   console.log(JSON.stringify({
     url,
     status: res.status,
     resText: resText.slice(0, 4000),  // 截取部分日志
   }));
   ```

3. **统一错误返回格式**：便于错误处理
   ```typescript
   try {
     // ...
   } catch (e) {
     return { code: -1, error: e };
   }
   ```

4. **域名白名单配置**：必须在代码中通过 `basekit.addDomainList()` 配置，且只能调用一次

### 常见问题排查

#### 字段读取失败

**问题**：`formItemParams` 中字段为 `undefined`

**排查步骤**：

1. 检查 `config.json` 中 `mockData` 的 key 是否与 `formItems` 中的 key 完全一致
2. 检查字段值的类型是否匹配
3. 检查是否使用了 `t('key')` 而不是硬编码

#### 字段格式不匹配

**问题**：返回的数据无法写入多维表格

**排查步骤**：

1. 检查 `resultType` 定义是否与返回的 `data` 结构一致
2. Object 字段必须包含 `id` 和 `primary` 属性
3. 检查数据类型是否匹配（string、number、boolean 等）

#### fetch 请求失败

**问题**：网络请求被拒绝

**排查步骤**：

1. 检查域名白名单配置：`basekit.addDomainList(['example.com'])`
2. 确保域名格式正确（不含协议、路径）
3. 确保只调用一次 `addDomainList`

#### 授权失败

**问题**：授权相关请求失败

**排查步骤**：

1. 检查 `config.json` 中 `authorizations` 配置是否正确
2. 检查授权 id 是否与代码中的 id 一致
3. 检查授权类型是否匹配

#### 构建失败

**问题**：`npm run pack` 失败

**排查步骤**：

1. 检查 Node.js 版本是否为 14.21.0
2. 重新安装依赖：`rm -rf node_modules && npm install`
3. 检查 TypeScript 编译错误
